# 对话求职完整链路修复方案

状态：用户已批准，已实现并完成下述本地验证；生产未部署。

## 1. 目标与已确认需求

把“识别找工作后展示组件”补齐为可以持续对话的求职流程：用户明确要求找岗位并推荐时，搜索完成自动分析；同一会话可以引用、返回和比较不同批次；“这个岗位”对应用户当前预览；每轮回答使用提交时固定的数据。

用户已确认：

- “帮我找岗位并推荐适合我的”应在搜索完成后自动分析，无需再问一遍。
- 同一会话支持“比较网易与腾讯两批”“回到刚才网易那批”。
- 只有明确确认目标岗位才更新资料绑定；预览、比较和推荐都不自动绑定目标。
- 沿用已确认的城市规则：明确城市优先；已有定位授权时获取当前位置；无授权或失败则提示启用定位或手选，不默认为上海。

先完成 PC 链路和验收，再单独验收手机端已有能力的兼容性；不做平板专项适配。只在本地实现、迁移与验证，不涉及生产部署。

## 2. 当前问题与方案选择

| 问题 | 本次直接修复点 |
| --- | --- |
| “帮我找腾讯有哪些岗位适合我”被直接归为闲聊 | 明确搜索/换条件优先于泛职业方向规则；结合搜索批次目录判断是否已有可分析结果 |
| 网易旧详情、旧分页混入腾讯结果 | 每次搜索创建独立 batch_id；所有请求、回包、保存和 UI 更新都携带该 ID |
| 提交网易追问后可能读到重搜腾讯的数据 | Turn 入队固定批次目录版本、岗位版本和预览引用；Worker 不重新读取活动卡片 |
| 保存失败结束后，追问仍进入模型 | 保留按批次区分的未保存操作；岗位相关追问必须取得保存回执，后端也验证引用版本 |
| 点开第 11～15 个岗位后，“这个”不可见 | 保存全部已加载岗位，独立记录 focused_job_ref；取消前十条作为模型数据上限 |
| 意图回看 30 条、回答回看 200 条 | 两者共享同一份服务端搜索批次目录，与文字历史窗口解耦 |
| 所有 JD 强制进入每轮上下文，小模型闲聊超限 | 先判断本轮任务，再按引用与预算选择证据；普通聊天不注入 JD |

比较三种落地方式：

| 方式 | 优点 | 代价与结论 |
| --- | --- | --- |
| 继续扩展 ui_payload 与正则 | 改动少 | 可变卡片承担事实、搜索状态和任务调度，无法可靠冻结与跨批引用，不采用 |
| 独立搜索批次＋现有 Turn 队列的内部分析任务 | 复用 PostgreSQL、Worker、模型连接与 SSE；浏览器结果能继续驱动回答 | 推荐；新增批次数据契约和明确的内部任务来源 |
| 整段改成持久 LangGraph interrupt/resume | 可以在同一图执行中等待外部结果 | 当前 Intake Graph 与 PostgreSQL Turn 队列已各有职责，全面迁移需重做暂停状态、租约及恢复；本次不迁移 |

推荐方案参考客户端工具结果回传后继续生成的成熟流程。Vercel AI SDK 官方明确区分客户端工具执行、工具结果提交和自动继续；本项目只复用模式，保留 Vue/Python 技术栈，不引入其运行时。[官方流程](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-tool-usage)

LangGraph interrupt 需要持久 checkpointer 和 thread_id，恢复时节点从头执行，因此不能仅在当前函数中插入 interrupt 就完成改造。[官方说明](https://docs.langchain.com/oss/python/langgraph/interrupts)

开源评估：AI SDK 使用 Apache-2.0，LangGraph 使用 MIT；官方文档和仓库均仍提供相关实现。两者许可允许评估复用，但本次不复制源码、不升级现有 LangGraph，也不扩大模型可执行的浏览器动作范围，适配成本集中在现有服务内部。[AI SDK 许可](https://github.com/vercel/ai/blob/main/LICENSE)、[LangGraph 许可](https://github.com/langchain-ai/langgraph/blob/main/LICENSE)

## 3. 用户可见流程

```mermaid
flowchart LR
    A[用户提出求职需求] --> B[识别搜索或分析意图]
    B -->|新搜索| C[建立独立搜索批次]
    C --> D[组件调用现有浏览器插件]
    D --> E[保存岗位与已获取的详情]
    E --> F[固定本次分析依据]
    F --> G[自动推荐具体岗位]
    B -->|追问或比较| H[解析批次与当前预览]
    H --> F
    G --> I[继续追问或确认目标岗位]
```

示例：

1. “帮我找杭州网易云的岗位，推荐适合我的。”→ 展示搜索卡；结果保存后自动给出推荐、简历证据、差距与待核实项。
2. 点击第 12 个岗位，说“这个岗位适合我吗？”→ 分析当前预览的第 12 个，不默认列表第一项，不要求先绑定目标。
3. “再找上海腾讯的。”→ 新批次，继承未被用户改变的可靠条件；网易云批次保留。
4. “比较刚才这两批，优先推荐三个。”→ 从两批已加载岗位中初筛，再用可用 JD 核对推荐依据，明确哪些仍只有摘要。
5. “回到刚才网易云那批。”→ 展开已保存结果，不自动调用 BOSS 重新搜索。
6. “你好。”→ 普通聊天，不把全部历史 JD 强制塞入请求。

自动分析依赖浏览器完成本次实时检索；页面关闭时不承诺后台继续操纵浏览器。已保存结果回来可继续查看，尚未完成的步骤显示状态和继续入口，不自动重搜历史记录。

## 4. 数据：批次、岗位版本与预览分开

新增两个领域表，复用现有 conversation、message、Turn 和 Turn payload：

### 4.1 job_search_batches

- id、conversation_id、source_message_id、source_turn_id。
- batch_no：会话内递增编号，展示为“第 1 批 · 网易云 · 杭州”；公司相同但条件或时间不同仍是不同批次。
- conditions：本次已实际提交的关键词、城市与城市来源，创建后不改变；改条件新建批次。
- revision：递增数据版本；search_status：created/searching/succeeded/empty/failed/cancelled。
- loaded_count、has_more：仅描述已取得的真实结果；不把“已加载 15 条”说成全站只有 15 条。
- focused_job_ref、last_focused_at：预览引用，独立于目标岗位绑定。
- analysis_requested、analysis_context、analysis_turn_id：是否要求自动推荐、创建批次时固定的模型选择/简历绑定上下文，以及对应内部分析任务。
- operation_receipts：按 request_id 记录写入类型、请求摘要和已确认 revision；用于重复回调返回同一回执，不能把同一 request_id 用于不同内容。
- created_at、updated_at、legacy_imported、legacy_total_count。

### 4.2 job_search_job_versions

- batch_id、job_ref、revision 为主键；同一岗位新详情写新版本，不覆盖旧版本。
- display_index 为批次内首次出现时分配的稳定顺序；分页去重不重排已分配顺序。
- bridge_key 保存现有插件需要的岗位识别字段，仅供桥接使用；job_ref 为平台生成的短引用，例如 S2-J12，模型使用这个引用。
- payload 包含标题、公司、薪资、城市、经验、学历、技能、原始 JD 和详情状态。完整 JD 沿用现有岗位材料 30000 字符边界，不再永久只保存前 2000 字。
- fetched_at、detail_status（not_requested/loading/ready/failed）及错误说明，区分“没有要求”和“没有取得要求”。

每次写入在批次行锁下分配 revision。相同请求重试按 request_id 返回原回执；相同内容不生成新版本。批次中岗位增加或详情更新都保留历史版本，不提供任意覆盖旧版本的接口。

读取 `(batch_id, revision)` 时，对每个 job_ref 选择不大于该 revision 的最新记录。因此版本引用可以还原提交时的结果，不必每轮复制全部 JD。

会话删除沿用现有删除语义级联删除这些领域数据。这是多轮引用和固定分析依据所需的数据，不新增跨会话记忆、备份或容灾系统。

## 5. 浏览器请求与保存状态

把搜索过程放入独立的 job-search-session 控制器，Workspace 负责展示与发出用户操作。控制器按 batch_id 保存状态，避免组件切换把请求归属改掉。

每个搜索、分页和详情请求捕获 `{batch_id, request_id, conditions, page, job_ref}`：

- 旧批次回包只允许更新旧批次；不能读取当前 submittedQuery/selectedCity 来决定归属。
- 当前 UI 只应用活动批次的更新；旧结果可以保存在原批次供历史分析，但不能追加到当前数组。
- 明确取消的批次不再接受后续回包。桥接不支持 Abort 时，网页停止应用其结果即可。
- 换条件创建新批次，不通过清空同一张卡片的 result_summary 表示新搜索。
- 返回相同页、详情重试和重复回调按岗位引用及 request_id 去重。

保存状态为 clean/saving/dirty/error，而不只是一个 pending Promise：

- error 保留失败操作及所属批次，显示“重试保存”；重试使用原 request_id。
- 岗位相关追问先把所引用批次的未保存操作提交成功，失败则保留输入，不静默入队分析。
- 普通聊天不被其他卡片的旧保存错误拦住。
- 提交请求携带本次页面所引用批次的已保存 revision、focus 和未保存状态；后端验证版本与岗位存在性。若异步意图识别才发现所需批次没有保存，返回明确的资料未就绪结果，不用其他批次替代。
- 当前预览的 job_ref 随 Turn 请求提交，focus PATCH 用于恢复页面；不能只依赖 focus PATCH 是否先完成。

全部已加载岗位都保存，初次返回 15 条就保存 15 条；分页按每次最多 50 条传输，不对整批偷偷保留前 10 条。客户端渲染的三条摘要只是展示投影。

## 6. 意图与引用解析

意图识别与回答共同使用服务端搜索批次目录，不再各自从最近 30/200 条消息找卡片。

路由动作限定为 search_jobs、analyze_jobs、compare_batches、clarify、cancel_search、normal_chat；另有 open_form 用于缺少可靠关键词的明确找工作意向。

优先级：

1. 明确取消、用户指定的任务先后。
2. 明确新搜索或更换公司/城市/方向，即使句子里有“适合我”也执行搜索。
3. 明确引用某批、某岗位、当前预览或要求比较，执行分析。
4. 没有可靠搜索对象的“我适合什么工作”，做方向咨询。
5. 其他正常对话。

规则只直接处理无歧义情况。歧义表达用一次受约束 JSON 识别，输入为本轮真实指令、冻结的批次目录、预览引用及少量近期用户条件。每个搜索条件和引用必须可追溯到用户输入、已确认条件或目录；不从简历/JD 文本读取界面指令。

结构字段为 action、query、city、batch_ids、job_refs、analysis_mode、auto_analyze、evidence。更换公司时必须覆盖旧公司条件；“网易”与“网易云”不自动视为同一公司或猜测隶属关系。

引用顺序：本轮明确编号/名称 → 本轮提交的当前预览 → 明确指向的批次 → 当前活动批次。多个同名批次无法唯一判断时，列出“公司＋城市＋批次编号”供用户选，不能悄悄选最近一张卡。

## 7. Turn 入队固定依据

在现有 `_enqueue_inbound → CareerTurnJobRepository.enqueue` 路径中，和 Turn 入队一起捕获：

```json
{
  "job_search_snapshot": {
    "schema_version": 1,
    "catalog": [
      {"batch_id": "uuid-A", "revision": 8, "batch_no": 1, "conditions": {"keyword": "网易云", "city": "杭州"}, "loaded_count": 15},
      {"batch_id": "uuid-B", "revision": 4, "batch_no": 2, "conditions": {"keyword": "腾讯", "city": "上海"}, "loaded_count": 15}
    ],
    "active_batch_id": "uuid-B",
    "focused_job_ref": "S2-J12",
    "uncommitted_batch_ids": []
  }
}
```

目录、状态和引用在入队事务中读取并写入已有 request_metadata_json；目录同时包含各批次的 search_status、loaded_count 和 has_more，不能只冻结编号而继续读取实时状态。简历/目标岗位继续用现有冻结字段。写入与入队都先锁会话行，再按 batch_id 升序锁所需批次，冻结时不会读到半页数据。Worker 后续只按冻结的批次版本取岗位，不读活动卡片的可变 ui_payload，也不自动换成最新简历。

PostgreSQL 的事务隔离只保证该事务内的视图，不能让稍后另一个 Worker 事务自动回到原状态；因此本方案显式保留岗位版本，而非长期开着事务等待模型。[事务隔离文档](https://www.postgresql.org/docs/16/transaction-iso.html)

`CareerInboundMessage → prepare_turn_payload/restore_turn_input → ModelTurnContext` 传递同一快照。同步与流式 Runner 共用解析与选证据服务。

## 8. 搜完自动推荐

使用现有持久 Turn 队列创建内部分析任务，不让浏览器直接调用模型，也不依赖页面上的一次性 Promise 维持任务。

1. 用户要求搜索并推荐时，在卡片/批次记录 analysis_requested=true。纯搜索仅展示结果。
2. 插件返回首屏后立即保存全部基础信息，继续复用现有并发 2 的详情加载。首屏详情全部结束，或基础结果保存后满 30 秒，浏览器提交本批 complete。30 秒是收集已可用 JD 的等待上限，不取消插件已有超时规则；失败项标记失败，仍可基于已取得数据初筛。
3. 仅在相关保存操作 clean 后 complete。服务端固定当前 revision、任务目标和批次创建时的简历/模型选择，排入 `source=job_search_auto_analysis` 的内部 Turn。
4. 初次自动分析幂等键为 `job_search_auto_analysis:{batch_id}:initial`。重复 complete、刷新和回调重发返回已有任务，不再次调用模型；首次失败后用户明确点重试才创建新尝试。
5. 后来的 JD 或分页形成新 revision，不改已排队分析的依据；后续追问使用新版本。模型明确说明已比较多少条基础信息、哪些取得 JD，不能把初筛写成完整匹配结论。
6. 回答标明所属批次，附在原搜索卡片之后；晚返回的网易分析不能显示成腾讯分析。每条推荐包含可点击岗位引用，点击预览对应批次与岗位，仍不自动绑定目标。

内部任务复用既有 Worker、模型用量与 SSE；允许排在正在处理的用户任务之后。没有伪造的用户消息；内部分析跳过用户消息落库和搜索意图路由，直接使用固定任务与批次快照，避免自动分析再次开搜索卡。历史返回 source、parent_turn_id、batch_id，使前端能恢复和订阅其状态。自动任务的进度归属原卡片，不能覆盖较新用户轮次的 lastTurn、模型选择或输入区状态。

原始搜索请求算一个用户轮次，其自动分析不再占第二个“30 轮”名额。数据库统计、准入、历史 API 与前端轮次展示必须使用统一的用户轮次口径，只对新增 job_search_auto_analysis 内部任务作排除；不顺手改变既有简历初评的计数政策。原始搜索是第 30 轮时，已获准请求对应的内部分析仍允许完成。get_last_model_selection 读取最后一次用户选择时也排除这种内部任务，避免旧批次晚分析把较新的用户模型选择回退。

模型历史与摘要压缩必须保留自动分析助手消息：parent_turn_id 只表示业务归属，文字历史按实际生成时间保留独立的助手续答块与消息 ID。历史分组增加这种无 user 消息的内部助手块，不把它强行拼回较早的用户轮次并改变时间顺序，也不能因缺少子任务 user 消息而被 group_complete_turns 丢掉。后续新生成的自动结果在摘要游标之后，必须参与下一次历史组装或压缩。

没有简历时自动分析岗位方向与要求，并明确无法作个人匹配；不阻断整个搜索。页面在 complete 之前关闭时，返回后读取已保存状态，允许完成这次结果提交；不自动重抓 BOSS。模型分析入队后，页面关闭不影响现有 Worker 执行。

若没有可用模型连接，搜索结果照常保留，自动分析标记为模型不可用并提供现有模型连接入口，不生成假推荐。analysis_context 只保存模型档案选择与已有资料上下文，不复制连接凭证。

## 9. 模型证据选择与预算

不再把整批 JD 无条件 pinned。

- normal_chat：不注入岗位 JD。
- analyze_jobs 且明确岗位：优先选该岗位的当前冻结版本与简历证据。
- recommend：先对所引用批次的全部已加载岗位做基础信息初筛，再用可用 JD 核对短名单；默认给 3 个推荐，用户明确数量时服从用户。
- compare_batches：保留各批次来源，对指定岗位或各批候选作比较，不把所有岗位扁平混成一批。
- 元信息超出预算时按完整岗位分块初筛后合并短名单，记录覆盖数量；不能用固定前 10 条代表全部。未取得 JD 的候选标为未核实，不给伪造分数。
- JD 超长时按段落和原文编号提取要求，复用 `number_source_lines` 与已有证据校验；不得只截前 2000 字，把尾部学历、经验、地点等要求丢掉。没有覆盖全文则必须保留未覆盖标记，不能声称已经核对所有硬条件。
- 每次路由、初筛、证据提取和最终回复分别经过既有预算服务；在当前问题和输出额度之外分配岗位证据，不把整批 JD 作为必需组件。
- 不新增求职评分算法；正式单岗位评估仍使用现有 `job_assessment` / `job_match_rules`。本次多岗推荐输出证据与差距，不用生成分数替代判断。

只有用户当前问题、引用身份及足以避免串岗的最小信息必需保留。普通“你好”在 16K 模型和十份长 JD 的会话中仍应正常回答。

| 接口 | 用途 |
| --- | --- |
| POST /batches | 搜索前登记新批次，返回 batch_id；条件变化永远新建 |
| GET /batches | 读取本会话批次目录与分析状态，供历史恢复和引用 |
| GET /batches/{id}/jobs?revision=R&cursor=C | 读取固定版本的岗位，回到旧批次不重搜 |
| POST /batches/{id}/pages | 保存一页基础结果，含 request_id/page，返回 revision 与 job_ref 映射 |
| POST /batches/{id}/details | 保存已有 job_ref 的详情新版本，不覆盖基础结果归属 |
| PATCH /batches/{id}/focus | 保存预览引用，不更改目标绑定 |
| POST /batches/{id}/complete | 完成本轮结果收集，必要时幂等创建自动分析任务 |
| POST /batches/{id}/analysis/retry | 用户明确重试失败的分析，保留原失败结果与尝试关联 |

现有文本与附件 Turn 提交都增加同一份搜索视图引用；后端解析、校验后冻结，不能让客户端直接提供替代服务端事实的 JD 上下文。

模块划分与实施顺序：

1. 新增 `job_search_sessions.py`（契约）、`persistence/job_search_repository.py`（批次与版本）、`web/job_search_router.py`（接口）。迁移接在当前 `20261109_35` 后，实施时先复核 Alembic head。
2. 新增前端 `job-search-session.js`，统一批次请求、版本回执、保存重试和焦点；修改 Workspace、CareerJobSearchCard、CareerAssistantPage，保持 PC 现有视觉结构。
3. 修改 `contracts.py`、`turn_payloads.py`、`turn_router.py`、`turn_job_repository.py`、`intake_graph.py`，让快照在入队时固定并贯穿 Worker。
4. 修改 `job_search_intent.py`、`job_search_response.py`，引入显式分析/比较与共享目录；删除互相矛盾的历史窗口依赖。
5. 新增 `job_search_analysis.py`，修改 Worker、Runner、消息投影、轮次计数与历史分组，实现内部自动任务及原卡片关联。
6. 修改 `job_search_context.py`、`prompt_context.py`，按任务选证据并纳入预算；复用现有原文编号和评估规则。
7. 兼容旧卡片并完成回归，同步更新求职助手、职位库模块说明。

## 11. 旧数据兼容

新卡片使用 version=2，ui_payload 只作批次引用和展示投影，不再充当完整岗位事实库。v2 结果写入专用接口；旧 PATCH 不得绕过批次数据直接覆盖模型事实。

旧 version=1 卡片在首次访问或迁移时，从已有 result_summary 导入一个 legacy 批次；按 source_message_id 去重，只导入实际保存的数据，保留原 total_count。原来只存 10/15 条就显示“历史共 15 条，本地可分析 10 条”，不伪造其余岗位。旧 excerpt 不当作完整 JD。选定目标岗位的原绑定保持原语义。

历史卡片恢复不自动重新定位、搜索或补采详情。用户主动重新搜索才创建新批次。此次无需新增插件动作，继续使用 search_jobs/get_job_detail；兼容性以现有桥接返回字段验证。

## 12. 验收矩阵

| 场景 | 必须观察到的结果 |
| --- | --- |
| 无结果或已有网易结果，输入“帮我找腾讯有哪些岗位适合我” | 进入腾讯新搜索；不能被方向规则截断 |
| 网易旧详情晚于腾讯搜索开始返回 | 只写网易批次，腾讯批次不出现网易 JD |
| 网易第 2 页晚于腾讯搜索完成返回 | 两批岗位分开，腾讯数量与公司不被污染 |
| 提交网易追问后，同一卡片新搜腾讯/更新详情 | 已提交 Turn 仍读取网易原 revision |
| 岗位 PATCH/详情保存已失败并结束，再追问 | 相关数据未保存不进入无依据分析，输入可重试；“你好”不受无关旧错误影响 |
| 15 条结果中点击第 12 个，问“这个适合吗” | 模型取得第 12 个的身份与可用 JD，目标绑定不变 |
| 搜完网易和腾讯，要求比较/回到网易 | 精确选择两批或旧批，不额外请求 BOSS、不重跑搜索 |
| 经过 16 轮后再说“再看看上海的” | 搜索目录仍可用于继承正确条件，不受 30 条窗口影响 |
| 搜索并推荐后不再发第二条消息 | 自动出现相关批次的推荐，刷新/重复 complete 不重复创建分析 |
| 完成一个搜索与自动推荐 | 用户轮次数只增加 1；历史没有伪造用户输入，自动推荐仍参与后续上下文 |
| 16K 模型＋十份各 2000 字 JD，输入“你好” | 正常聊天，不因为无关 JD 超限 |
| 15 个候选、关键硬要求在第 2000 字以后 | 不丢候选、不把不完整 JD 当作已核验完整要求 |
| 页面关闭后恢复 | 已保存批次可读、已入队分析可恢复，不自动重搜或重复模型请求 |
| 旧卡片只保存前 10/15 条 | 真实显示可用数据范围，未知 JD/岗位不编造 |

验证层次：领域/仓储测试 → 真实本地 PostgreSQL 事务与 API 测试 → 真实 Runner 输入快照与 Token 预算测试 → PC Playwright 故意乱序/失败/刷新测试 → PC 验收后检查手机历史查看与普通对话兼容性。

真实模型验收要单独验证“推荐是否引用正确批次和岗位、简历证据是否真实、缺少 JD 是否如实说明”，不能把测试客户端返回固定文字等同于模型质量已验收。真实 BOSS 检索与插件故障排查沿用现有授权和用户登录环境，不向外部发送招呼语作为测试。

## 13. 范围与交付状态

本方案只解决当前对话求职链路，复用现有插件检索、模型连接、队列、SSE、隐私处理和目标岗位绑定。没有新增跨会话推荐、无人值守浏览器调度、招聘账号体系、自动投递或自动发送。
