# 面试大师低延迟设计

## 目标

缩短面试官结束一句话后到页面出现回答首字的时间，同时保持“只对面试官 final 话语作答”、FIFO 顺序和四条追问上下文不变。

## 线上诊断基线

- 2026-11-17 最近一次生产会话中，ASR final 到回答任务开始为 4～6ms，完整回答生成耗时为 1.54～3.35s。
- API 容器无重启、无 OOM，主机负载低；慢点主要位于浏览器音频经香港服务器转发至百炼、以及百炼 VAD 产出 final 之前。
- 当前 DashScope 使用 `qwen-audio-3.0-asr-flash-streaming` 与 800ms 静音断句；浏览器 WebSocket 允许约 1MB 待发送数据，极端情况下会积累十余秒 PCM。
- 当前只在浏览器内临时采集“问题识别到首字”的时间，没有展示、服务端分段指标或持久化证据。

## 设计

1. DashScope 默认模型升级为官方当前推荐的 `qwen-audio-3.1-asr-flash-streaming`，默认静音断句改为 500ms；二者均保留环境变量覆盖。3.1 模型默认使用适合直采电脑声音的 `near_meeting_16k` VAD。
2. 回答请求固定使用 `thinking=False`、`temperature=0.2`、`max_tokens=1024`。提示词要求先给结论，并把完整建议控制在 800 个中文字符内。
3. 回答队列记录入队、开始、首块和完成的单调时钟时间。WebSocket 的 `answer.started`、首个 `answer.delta`、`answer.completed` 分别携带排队、模型首字和总生成耗时，不保存问题正文以外的新数据。
4. 浏览器以 `question.detected` 到首个 `answer.delta` 的时间作为用户可见首字延迟，同时展示服务端模型首字时间。默认优先选择名称或模型 ID 含 `flash` 的可用回答模型，但尊重用户显式选择。
5. 浏览器待发送缓冲上限从 1,000,000 字节降到 256,000 字节，避免弱网时旧音频持续排队；超限仍沿用现有提示和丢弃策略。

## 实时性指标

- 正常网络下，ASR final 到页面首字目标：P95 不高于 3 秒。
- 服务端模型首字目标：P95 不高于 2.5 秒。
- FIFO 等待单独计入 `queue_wait_ms`，不把前一题尚未完成误判为模型慢。
- 外部 Provider 超时、网络中断和浏览器系统音频暂停无法被代码绝对保证；页面必须显示实测时间，便于区分 ASR、排队与模型延迟。

## 边界

- 不使用未完成 partial 提前作答，避免停顿时回答半句话。
- 不改变数据库结构、会话记忆、四条追问上下文、本场问答和归档结构。
- 不自动切换用户已明确选择的模型。
- 本轮只完成本地代码、测试、构建与文档；未经明确授权不部署生产。
