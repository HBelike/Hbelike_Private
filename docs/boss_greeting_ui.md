# BOSS 一键打招呼：真实串行发送

## 设计目标

PC 端复用现有职位库和求职助手页面，为用户逐条审核后的 1–10 个岗位生成并发送招呼语。本功能通过本地 Chrome 扩展复用用户已登录的 BOSS 页面，不部署平台账号凭证，也不把 Cookie、Token 或聊天记录回传到 WebUI。

核心流程：

```text
从现有职位库选择 1–10 个岗位
  → 每岗生成一条招呼语并逐条审核
  → 6–10 条时二次确认账号风险
  → 单条预检 → 单条真实发送 → 确认结果 → 下一条
```

## 页面与交互

- 选岗：复用 `JobSearchWorkspace`，用户配置本批上限，范围 1–10。
- 审核：左侧固定发送顺序；中间只编辑当前岗位的一条招呼语；右侧展示简历证据和岗位关注点。
- 单条操作：支持直接编辑、取消本批发送、只重新生成当前一条。
- 文案：不机械截断，建议控制在 150 字以内；突出核心优势、经验匹配度与礼貌问询。
- 默认招呼语：无需关闭；若 BOSS 自动发送默认招呼语，定制文案作为下一条消息继续发送。
- 风险：最终发送数量为 6–10 时，必须再次确认限流、安全验证、额度限制及封禁风险。
- 进度：展示“正在预检、正在发送、已发送、已跳过、发送失败、已停止”，始终提供“停止剩余发送”。
- 安全预览：`greeting-preview.html` 显式启用 `simulationMode`，只演示 UI 状态，不调用扩展发送动作。

## 调用链与技术取舍

```text
CareerGreetingDialog
  → jobLibraryBridge.preflightGreeting（只读）
  → 扩展检查登录、验证、岗位详情和聊天标识
  → jobLibraryBridge.sendGreeting（单岗位、单文案）
  → 单次 friend/add
  → BOSS 官方聊天页填入文案并单次点击“发送”
  → 识别本人消息的送达/已读状态
  → WebUI 收到明确结果后才启动下一岗位
```

- WebUI 持有批次队列，扩展每次只接受一个岗位，避免扩展脱离页面继续批量执行。
- 发送使用 BOSS 正常网页聊天路径，不实现私有 WebSocket 协议。
- 搜索、详情和发送前预检遇到会话状态失效时，自动刷新 BOSS 标签页一次并重试只读请求；不依赖后台定时器或跨操作冷却。
- `friend/add` 和“发送”点击均不自动重试。结果未知时停止批次，避免重复发送。
- 自动刷新后仍失败时，对尚未提交消息的失败项提供“重试这一条并继续”；结果未知的发送不提供重试按钮。
- 岗位失效或此前已沟通只跳过当前项；登录失效、验证码、限流、DOM 异常或结果未知会停止剩余任务。
- 用户点击停止后不启动下一项；若当前消息已提交，则等待该条返回明确结果，不把它伪装成已取消。

## Prompt 与 humanizer

完整两阶段 Prompt、事实引用规则和结果校验定义在：

- `docs/superpowers/specs/2026-08-23-career-boss-batch-greeting-design.md`

第一阶段只允许从编号后的简历与 JD 证据选择事实；第二阶段使用 humanizer 消除模板腔、夸张和营销表达，但不得新增、删除或改变数字、公司、学历、技术与项目事实。匹配度较低仍然生成，不输出劝退结论。

## 本地使用

1. 在 `chrome://extensions` 开启开发者模式，加载或重新加载 `browser-extension/job-library`。
2. 保持一个已登录且无验证码拦截的 BOSS 页面。
3. 启动 WebUI，在求职助手中进入“一键打招呼”，选岗、审核文案并确认真实发送。
4. 仅验证 UI 时访问 `http://127.0.0.1:5173/greeting-preview.html`；该页面永远不会发送到 BOSS。

真实账号验收会产生对外沟通，应由用户在最终岗位与文案可见时主动点击确认；本地自动验证不代替用户执行真人账号发送。
