# BOSS 一键打招呼：智能生成与真实串行发送

## 设计目标

PC 端复用现有职位库和求职助手页面，为用户逐条审核后的 1–10 个岗位生成并发送招呼语。本功能通过本地 Chrome 扩展复用用户已登录的 BOSS 页面，不部署平台账号凭证，也不把 Cookie、Token 或聊天记录回传到 WebUI。

核心流程：

```text
在左侧岗位卡直接多选 1–10 个岗位
  → 读取每个岗位的完整 JD
  → DeepSeek 为每岗生成一条招呼语并逐条审核
  → 6–10 条时二次确认账号风险
  → 单条真实发送 → 点击发送后立即处理下一条
```

## 2026-11-04：生成与提交统一 200 字上限（历史规则，已替换）

以下记录当时的实现。2026-11-15 按用户确认改为仅在 Prompt 中建议 200 字左右，生成、编辑、队列、桥接与插件均取消字数硬门禁，详见下节。

- 模型侧：System、初次生成/重新生成 User、纠正提示词均明确最多 200 个字符；保留现有生成最低 60。中文、英文、数字、标点、内部空格均计入，Python len 与 JavaScript Array.from 统一 Unicode codepoint 口径；发送前去除首尾空白。
- 生成校验：不再先截断正文或压缩内部空格来隐藏超长。201 字进入既有一次纠正流程，仍超长则返回生成失败，不提供可发送文案；事实和原样成果 URL 约束继续保留。
- 编辑与提交：UI 显示最终正文的 200 字计数，保留超长全文供修改并阻止发送；审核、纳入队列、失败重发、串行发送和模拟分支各自校验。共享 bridge 的 preflight/send/retry 在 postMessage 前检查，插件 normalizeGreetingPayload 在访问 BOSS 页面前再次检查，超限返回 message_invalid 和 not_submitted，不机械截断、不触发默认招呼或实际提交。
- 发布：插件、网页下载版本升为 0.4.2，需更新/重新加载已安装实例。保留 0.4.1 的 ping 独立响应及连接误判修复。
- 验证：本轮相关 Python 111 项、前端 Node 287 项、插件 Node 53 项、Chromium 21 项均通过，Vite 构建通过；含 200/201、Emoji、空格、生成纠正、手工粘贴、重发和实际 dispatcher 不访问 BOSS 页面验证。浏览器采用模拟模式、模拟生成和扩展响应，未调用真实模型或执行真实 BOSS 发送。

## 2026-11-15：围绕岗位匹配证据生成开场白

- 设计目标：让招聘者快速看懂应聘方向、相关经历和下一步。优先组织为约三句：具体岗位与相关身份 → 一条真实职责、交付或结果 → 一个容易回应的沟通邀请；篇幅尽量控制在 200 字左右，仅由 Prompt 引导，没有程序字数上下限，不因略长或较短触发生成纠正或失败。该篇幅是写作建议，没有最高回复率或必回复的效果承诺。
- 选材取舍：完整扫描简历后，按 JD 核心工作选择一至两项相关证据。学校、学历、论文、专利、奖项和成果链接按相关性选用，替代此前“每个学术优势类别必写、至少附一个链接”的规则；一个项目已能证明相关能力时不强行追加其他类别。没有量化数据时允许用真实职责、上线交付或可演示成果说明能力，不补造指标、年限、城市、到岗时间或薪资预期。
- 提示词：System、初次/重新生成 User 和一次纠正提示统一使用上述选材与表达规则。User 中检出的学术类别与成果 URL 仅为候选项；模型仍必须返回实际使用的 `CV-xxx` / `JD-xxx`。结尾最多一个问题，不重复询问 JD 已明确的信息，不使用催促、奉承或乞求式表达。
- 程序逻辑：数字、技术词等字面校验收紧到被引用的 CV/JD 及岗位元数据；对于“我是、我有、我负责”等显式候选人子句，额外只核对被引用的 CV，避免 JD 技术或数字为个人经历背书。学历/学术表述可省略，写入时逐项核对 CV；每个写入的成果 URL 都必须原样存在于被引用的简历证据。超过一个问号进入既有一次纠正流程，URL 查询串的问号不计入。
- 调用链与依赖：沿用现有生成 API、固定 DeepSeek V4 Pro、JSON Output、一次纠正和前端人工审核，不新增依赖、接口字段或第二次润色调用。字面规则不能完整验证中文事实语义、职责归属或熟练度，最终文案仍须由用户审核。
- 长度处理：System、初次/重新生成 User、纠正提示词均建议 200 字左右，不精确计数凑字。后端删除 60–200 字校验；前端保留实际字数显示、取消长度错误态和发送拦截；bridge 与扩展完整传递非空正文。保留空文案、JSON、格式、证据与事实等独立校验，不截断正文和 URL。本地候选扩展升为 0.7.1，已安装旧版本需更新或重载后才能移除插件内的旧门禁。
- 研究依据：[候选人私信与录用的原始研究](https://pubsonline.informs.org/doi/10.1287/isre.2021.1003) 支持重视礼貌和校对；[WTW 招聘者一手建议](https://careers.wtwco.com/blogs/life-at-wtw/should-you-message-wtw-recruiter-on-linkedin) 建议具体岗位、相关成果、清晰下一步；[前程无忧自我介绍建议](https://arts.51job.com/arts/05/417988.html) 强调岗位关键词和真实相关经历。这些材料不构成 BOSS 技术岗话术的回复率对照实验。
- 首轮验证：生成服务、API 与模型客户端专项 56 项通过，覆盖无关学历/链接可省略、JD 独有技术/数字不得冒充显式本人经历、合法岗位名称/编号与 JD 转述、岗位学历条件不误作本人学历、已选证据引用、每个成果 URL 的来源、URL 查询串问号和多个问题的一次纠正。后续按用户纠正将原字数边界用例改为偏离目标字数仍原样返回、空文案仍失败。使用模拟模型响应，尚未验证真实模型文案质量或真实 HR 回复率。
- 软目标验收：后端生成/API/模型客户端与插件发行包检查 61 项、前端 Node 专项 43 项、插件 Node 专项 27 项、Chromium 场景 3 项通过，Vite 构建通过。覆盖 201 字及更长正文不因长度重试或失败、不截断、完整进入审核/队列/预检/首次发送/重发、原文重新生成、空文案仍拒绝；重新生成 API 不再因上一稿较长而返回长度校验错误。0.7.1 ZIP 与源码、安装引导版本一致。浏览器和插件验证使用模拟响应，没有执行真实 HR 发送。

## 页面与交互

- 选岗：复用 `JobSearchWorkspace`，岗位卡左侧提供直接多选框；点击卡片正文仍只预览详情，不再要求先预览再点击右侧“加入本批”。用户配置的本批上限保持为 1–10。
- 详情补齐：搜索返回岗位摘要后，以最多 2 路并发在后台预取当前页完整 JD；岗位预览、勾选和后台预取共用同一请求与缓存。勾选立即生效，不再等待详情；只有进入生成阶段前必须等待本批完整 JD 就绪。单个岗位加载失败只在该卡片提示，取消勾选或重新搜索会使迟到结果失效；登录、验证、限流或会话刷新失败会停止继续预取。
- 审核：左侧固定发送顺序；中间只编辑当前岗位的一条招呼语；右侧把简历证据和岗位关注点拆成上下两个等高分区，两类依据始终同时可见。每个分区固定标题和条目数量，长列表在分区内部独立滚动；空数据展示明确空状态，不改变生成接口或证据数据结构。
- 单条操作：支持直接编辑、取消本批发送、只重新生成当前一条。重新生成会把上一版文案作为避重复参照，但不会把它当成事实来源。
- 文案：Prompt 建议 200 字左右，程序不以字数拒绝生成或发送；优先从当前简历与完整 JD 选择一至两项最相关证据，组织自然开场，不使用固定句式拼接，保留完整正文供用户审核。
- 生成状态：每个岗位独立显示“生成中、可审核、失败”；最多并发生成 3 条。单条失败不阻塞其他岗位，失败且没有文案的项目不能进入真实发送队列。
- 默认招呼语：无需关闭；若 BOSS 自动发送默认招呼语，定制文案作为下一条消息继续发送。
- 风险：最终发送数量为 6–10 时，必须再次确认限流、安全验证、额度限制及封禁风险。
- 进度：展示“正在发送、已触发发送、已跳过、发送失败、已停止”，始终提供“停止剩余发送”。
- 安全预览：`greeting-preview.html` 显式启用 `simulationMode`，只演示 UI 状态，不调用扩展发送动作。

## 智能生成调用链

```text
CareerGreetingDialog
  → POST /api/career/greetings/generate
  → CareerGreetingService
  → 按当前用户读取候选人简历 + 校验完整 JD
  → 精确选择 READY 的 deepseek / deepseek-v4-pro 文本档案
  → DeepSeek Chat Completions JSON Output
       temperature=0.2, max_tokens=800, thinking=false
  → 校验非空正文、已引用证据、选用学历/成果链接、字面事实、单一提问与上一版相似度
  → 不合格时携带校验错误纠正一次
  → 返回文案、证据摘要、JD 关注点与模型元数据
```

- 模型固定为 `deepseek-v4-pro`，不跟随聊天页模型选择器，也不降级到其他模型。没有可用档案或 API Key 时明确提示用户配置，避免静默生成模板文案。
- 复用现有 OpenAI-compatible Chat Completions 客户端；JSON Output 是本次调用协议，模型档案保持 `TEXT` 能力即可。
- 浏览器只收到生成后的证据摘要，不返回完整简历、完整 JD、原始模型响应或 API Key。
- 生成与真实发送相互隔离：生成可以最多 3 路并发，扩展发送仍严格单条串行。

## 真实发送调用链

```text
CareerGreetingDialog
  → jobLibraryBridge.sendGreeting（单岗位、单文案）
  → 扩展检查登录、验证、岗位详情和聊天标识
  → 单次 friend/add
  → BOSS 官方聊天页填入文案并单次点击“发送”
  → 点击动作完成后立即返回 submitted
  → WebUI 直接启动下一岗位，不等待送达或成功回执
```

- WebUI 持有批次队列，扩展每次只接受一个岗位，避免扩展脱离页面继续批量执行。
- 发送使用 BOSS 正常网页聊天路径，不实现私有 WebSocket 协议。
- 搜索、详情和发送前预检遇到会话状态失效时，自动刷新 BOSS 标签页一次并重试只读请求；不依赖后台定时器或跨操作冷却。
- `friend/add` 和“发送”点击均不自动重试。扩展只确认输入框写入成功、发送按钮可用且点击动作已执行，不再监听聊天 DOM 的送达、成功或失败状态。
- 单岗在点击前遇到岗位失效、此前已沟通、登录失效、验证码、限流、DOM 异常或标签页异常时，记录为跳过或失败，但不会停止后续岗位；后续岗位仍按顺序各执行一次发送尝试。
- 用户点击“停止剩余发送”是唯一会终止后续队列的条件；当前已触发点击的项目记录为“已触发发送”，不再把 BOSS 回执当作批次推进条件。
- 继续保持单标签页、单岗位串行，避免并行导航覆盖文案，并降低集中并发触发带来的账号限制风险。

## Prompt 与证据边界

当前实际 System Prompt 位于 `src/career_assistant/greetings.py` 的 `_SYSTEM_PROMPT`，设计与校验规则定义在：

- `docs/superpowers/specs/2026-08-25-smart-boss-greeting-generation-design.md`

服务端把简历和 JD 分别编号为 `CV-xxx`、`JD-xxx`。模型必须先选择真实存在的证据，再生成单段开场白并返回 JSON；不能把岗位要求写成求职者已经具备的经历，也不能补写未出现的数字、公司、学校、技能或项目结果。程序检出简历中明确写出的 `985/211/双一流/QS`、博士/硕士、论文/专利等优势作为可选信息，模型按岗位相关性选择；文案使用的具体学术表述必须有对应 CV 支持，不根据校名或模型常识补全。

个人网站、作品集、项目地址以及 GitHub/GitLab/Gitee、PR/开源贡献记录属于可选成果链接。仅在有助于证明岗位相关经历且篇幅允许时附上；服务端验证每个实际写入的 URL 都原样来自被引用的简历证据，改写或无引用来源会进入既有的一次纠正流程，省略链接不会导致失败。

“去模板化”和 humanizer 原则已经合并进同一次 System Prompt：根据证据组合自适应选择切入点、句式和礼貌问询，避免“我非常符合贵司要求”“期待您的回复”等套话。运行时不依赖 Codex Skill，也不执行第二阶段模型调用。服务端进行字面与引用检查，中文语义事实仍依赖模型遵守证据边界和用户最终审核。

## 本地使用

1. 在 `chrome://extensions` 开启开发者模式，加载或重新加载 `browser-extension/job-library`。
2. 保持一个已登录且无验证码拦截的 BOSS 页面。
3. 启动 WebUI，在求职助手中进入“一键打招呼”，选岗、审核文案并确认真实发送。
4. 仅验证 UI 时访问 `http://127.0.0.1:5173/greeting-preview.html`；该页面永远不会发送到 BOSS。

真实账号验收会产生对外沟通，应由用户在最终岗位与文案可见时主动点击确认；本地自动验证不代替用户执行真人账号发送。
