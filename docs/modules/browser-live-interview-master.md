# 浏览器面试大师

## 当前实现

用户从求职助手打开 `/career/interview-master`，在桌面 Chrome、Edge 或 Firefox 中选择带声音的共享来源。网页把共享的电脑声音作为面试官通道，把可选的本机麦克风作为候选人通道。一个麦克风同时收录两个人时，网页无法按说话人分轨。开启麦克风后，候选人发言可以帮助理解随后的追问，候选人字幕只保留在本场内存中。

浏览器自首次 `session.ready` 起计时，包含暂停时间。第 115 分钟提示，第 120 分钟自动结束。服务端默认使用 `qwen-audio-3.1-asr-flash-streaming`，静音断句默认 500 ms，可通过服务端配置调整。单场能否持续一小时以上，取决于音轨、网络、ASR 和模型在这段实际时间内的表现。

### 转写与回答

- AudioWorklet 以跨块保留采样相位的方式转换为 24 kHz、单声道 PCM16，每 100 ms 形成一个常规帧。两条音轨使用独立序号。
- 字幕先显示中间结果。面试官定稿的背景和约束先留在同一发言轮次中，遇到提问或请求表达后合成一道题。候选人发言切换轮次，清除上轮尚未使用的背景。仅有陈述、或规则没有识别出问题时，可以点击“立即回答”提交当前题干。
- 回答模型按队列顺序流式作答，上一题生成期间可继续收音和转写。页面显示等候题数，按题号、生成次数与增量序号关联答案；“重新生成”明确发起该题的新一次生成。
- 明确的追问可以使用最近四条定稿发言、上一题，以及与上一题匹配的已完成参考答案摘要来理解指代。提示词区分候选人的真实发言和模型建议。普通问题仅使用当前题干。本模块不读取简历、岗位或面经资料。
- “定稿至首字”计量浏览器收到构成问题的最后一条 ASR 定稿，到收到首个回答增量的间隔，包含排队。在手动提问或恢复后找不到对应定稿时，页面将服务端排队耗时计入“含排队首字”。这两项指标均从 ASR 对外给出结果之后计时；真实人声结束到定稿的耗时需要单独测量。

### 短时断开与停止采集

- 浏览器持续采集已授权音源。连接中断或浏览器发送缓冲超过 256,000 字节时，每条音轨最多保留最近五秒尚未交给 WebSocket 的 PCM，以采集序号按序补发；超过五秒会显示各轨未发送的累计秒数。已经交给旧连接的帧缺少逐帧识别确认，断开瞬间的在途片段可能缺失。
- 后端每条音轨使用独立 writer，待写入 PCM 上限 288,000 字节（六秒，含正在写入的帧），单次发送最多等待六秒。短时上游停写期间控制消息与心跳仍可处理。面试官轨超出预算或意外结束时会通知浏览器；可选候选人轨中止时则单独停止该轨。
- 首次握手失败会保留音源并重试一次。活动期意外断开最多自动尝试三次，沿用原 `session_id`，恢复后继续提交暂存声音，并异步补齐数据库中已保存的历史。麦克风热拔时，共享声音继续转写。恢复耗尽或共享音源结束后，用户可以重新选择声音来源接续本场。
- 主动暂停或结束时，网页先停止采集、发送最后不足 100 ms 的 PCM 和可发送的暂存帧，再发送 `session.pause` 或 `session.end`。服务端排空音频转发，收取 ASR 尾句并通知 `session.ended`。网页会有界等待确认；遇到传输失败会提示尾句可能不完整。暂停后重新授权仍使用原会话，结束后可选归档。已中断且有正文的回答可在恢复的历史中查看，手动重新生成会产生新的一次模型调用。

## 调用链

```text
求职助手 → /career/interview-master → 浏览器授权声音来源
  → POST /api/career/live-interviews/sessions（client_kind=browser）
  → 同源 WSS /api/career/live-interviews/{id}/stream → session.ready
  → AudioWorklet → PCM16/24kHz → 每轨转发 → ASR 中间结果与定稿
  → 面试官题干合并 → FIFO 回答队列 → 回答模型流式输出
  → 同会话恢复，或主动结束并保存最后一句
  → POST /archive/preview → 用户确认 → POST /archive
```

页面提供转写、回答提纲、完整答案和本场问答。浏览器支持时可使用 Document Picture-in-Picture。归档时由用户填写公司、职位和日期，面经库仅接收去重后的问题。原始 PCM 与中间转写不持久化，模型凭据留在服务端。

## 依赖与运行环境

- `getDisplayMedia` 必须由用户操作触发。Windows 桌面 Chrome、Edge 可选择整个屏幕或会议标签页并开启声音共享；Firefox 的可用音源以其授权窗口为准。没有返回音频轨时应改选带声音的共享来源。
- 生产浏览器要求 HTTPS。Caddy 将 `/api/*` 的 WebSocket 转发至 FastAPI，本地 Vite 使用同源代理。DashScope 读取服务端的 `DASHSCOPE_API_KEY`，回答模型来自求职助手的模型选择配置。
- 数据库迁移 `20260823_19` 增加了浏览器会话标识和候选人音轨开关。恢复时重用既有会话、定稿与回答记录。页面缓存最近 100 条定稿和 50 条回答，字幕栏显示最近 18 条定稿。用户上翻时，新到的定稿逐条计数。

## 2026-08-31 验证边界

- 当前 Codex 环境未安装可控制 Chrome 的扩展，因此没有自动点击 Chrome 原生分享选择器。真实桌面通话验收需要用户手动选择“整个屏幕 + 共享系统音频”；该授权无法由网页代替。
- 尚无真实问题结束到回答首字的 P50/P95、长时间通话稳定性以及中文、英文、中英混合和跨行业术语准确率数据。
- 纯浏览器方案的可靠边界是 Chrome 在当前 Windows 版本上能否为“整个屏幕”返回系统音频轨；若没有该轨道，网页没有权限退回到静默监听整机音频。
