### CTX-001 历史窗口未取最新消息

- 入口：`src/career_assistant/persistence/conversation_repository.py` 的 `list_completed_dialogue_messages`。
- 证据：默认 `limit=200`，SQL 为 `ORDER BY message.created_at ASC, message.id ASC LIMIT :limit`。Prompt 组装和摘要任务都调用该方法。
- 验收目标：超过 200 条候选消息后，仍能连续处理摘要覆盖位置之后的消息，并保留最新完整轮次。
- 边界：当前普通用户会话有 30 轮成功回复上限，常规会话通常达不到 200 条；自动分析、失败重跑及历史数据等情形仍需纳入后续验证。不能把此问题描述为每个普通会话都会发生。

### CTX-002 页面上下文预览与实际回答不一致

- 入口：`src/career_assistant/web/turn_router.py` 的 `get_context_usage`；`prompt_context.py` 的 `snapshot_for_conversation`。
- 证据：预览传入最新 Turn 和模型，但未传绑定资料的 `ModelTurnContext`，服务使用空上下文；历史查询还会排除传入的最新 Turn，即使它已经成功完成。
- 局部复现：使用实际 `PromptContextService`、模拟仓储和同一份会话摘要；新问题的 `prepare` 同时包含摘要、最新历史、绑定简历和岗位，且跳过摘要覆盖的旧原文。页面 `snapshot_for_conversation` 仅保留摘要，缺少上述最新历史及两份资料。无真实模型或数据库请求。
- 验收目标：预览基于下一轮可用的已有会话上下文核算，包含绑定资料和已完成的最新历史；保留 Token 近似估算的现有语义，不要求预测未输入的问题或未来工具结果。

### CTX-003 摘要语义规则和验证不足

- 入口：`src/career_assistant/conversation_memory.py` 的 `_compaction_messages` 和 `validate_summary`。
- 证据：实际 system 提示词仅要求依据输入更新指定 JSON Schema、不补全身份经历成绩、数组必须存在及未知留空；user 消息包含上一版摘要和选中对话。未解释字段含义、如何处理纠正与过期结论、如何区分助手建议和用户事实，也未向模型明确列出后端长度限制。
- 当前验证只检查 Schema、字段类型、条目数量和长度，没有语义保真验证。此项不能描述为已观察到真实摘要失真。
- 验收目标：明确滚动更新和事实来源规则，用包含用户纠正、助手建议、未完成事项及重复压缩的样例验证保留行为；不默认增加额外模型或新的记忆框架。

### CTX-004 长回答可能无法保存到消息历史

- 入口：`config/career_assistant.yaml` 的 `response_generation.max_persisted_response_characters`；`response_runner.py` 的 `_append_assistant_message`；`persistence/conversation_repository.py` 的 `append_message`。
- 证据：当前配置允许保存 500000 字符，Runner 按该配置裁剪；仓储统一对消息执行 `maximum_length=30000` 检查，超长直接抛出 ValueError。
- 局部验证：调用实际仓储 `_normalize_content`，30000 字符通过，30001 字符被拒绝。尚未调用真实模型生成长回答或进行 PostgreSQL 集成验证。
- 验收目标：配置、Runner 和存储层对允许保存的回答长度保持一致；验证超长回答的最终保存、刷新回显及错误状态。

### CTX-005 简历档案与聊天上下文的保留范围不一致

- 入口：`src/career_assistant/intake_graph.py` 的 `_build_model_context`；`web/router.py` 的 `parse_candidate_profile`。
- 证据：确认接口保留不超过 30000 字符的完整解析正文；输入图对绑定简历直接取前 `_MAX_MODEL_RESUME_OUTLINE_CHARACTERS=10000` 字符，未按本轮问题或模型剩余预算选择。
- 局部复现：向实际 `_build_model_context` 传入 12009 字符的合成绑定简历，输出仅 10000 字符，末尾成果标记缺失。无真实模型请求。
- 验收目标：对话需要的简历证据不会因固定前缀截取而静默遗漏；若预算确实不足，应明确保留范围，并与岗位评估使用的资料范围保持可解释的一致性。

### DOC-001 复杂 PDF 的路由识别范围不足

- 入口：`src/career_assistant/document_probe.py` 的 `PdfDocumentProbe.probe`；`attachments.py` 的 `_parse_pdf`。
- 证据：路由依据每页字符量、文本覆盖率和提取异常；默认每页至少 24 字、覆盖率至少 80% 且无提取异常时走原生文本。没有检查双栏、字符坐标或阅读顺序；本地 Docling 仅在探测判定需要增强解析时接管。
- 验证边界：已核对实现并通过原生文本与扫描件路由脚本，尚未用真实双栏样本验证内容错序程度；不能声称当前能自动识别所有复杂版面。
- 验收目标：明确复杂版面路由策略，并用匿名双栏、表格及混合页面样本验证阅读顺序；不默认新增另一套文档解析框架。

### DOC-002 图片 OCR 质量门槛只检查最低文本可用性

- 入口：`src/career_assistant/attachments.py` 的 `_has_usable_image_ocr_text` 和 `_parse_image`。
- 证据：当前仅要求去空白后至少 24 字符、至少 6 种不同字符；通过后不再调用云端视觉复核。未检查图片实际文字覆盖、字段缺失或 OCR 逐块置信度。
- 局部验证：29 字符的合成工作经历片段即可通过门槛。这仅证明规则范围，不证明某份真实简历已经被漏读。
- 验收目标：验证 OCR 仅恢复局部文字时的处理行为，并明确哪些内容需要复核或用户确认；不得把该门槛或章节识别分数展示为全文 OCR 准确率。

### DOC-003 实时面试说明与当前实现不一致

- 文档：`docs/modules/browser-live-interview-master.md` 的基础说明仍描述新问题取消旧回答、追问使用最近两轮；后续修复记录与实际源码已改为逐句触发和 FIFO 串行回答。
- 源码：`live_interview/session_manager.py` 对自动问题排队，新问题不取消当前回答；检测当前问题前冻结最近 4 条转写。`answer_service.py` 只在 FOLLOW_UP 时注入这 4 条转写。
- 验收目标：模块入口说明、架构图、上下文边界和后续修复记录使用同一套现有语义，并区分浏览器实时链路与普通对话数据库 Worker。

### DOC-004 架构面试指南需与当前 Runtime 对齐

- 文档：`docs/career_assistant_architecture_interview_guide.md` 的 Prompt、Memory 和 SSE 小节仍描述固定最近六条消息、滚动摘要尚未接入、浏览器已按 Last-Event-ID 续传。
- 证据：当前主链已注入结构化滚动摘要与未覆盖历史；前端游标衔接缺口见 REC-002。旧 Skill 调用描述也应与当前基于文本 `/name` 的解析规则逐项核对。
- 验收目标：集中处理时修订既有指南；本轮新增 `docs/agent_runtime_learning_guide.md` 作为当前功能、真实图节点和循环边界的学习材料。

### DOC-005 BOSS 数据保存边界说明需要区分链路

- 入口：`browser-extension/job-library/README.md:28`、`web-ui/src/job-search-session.js`、`src/career_assistant/job_search_sessions.py`、`persistence/job_search_repository.py`。
- 证据：README 在招聘沟通说明中写“不上传原始接口响应与临时 securityId”，但未明确限定范围；对话岗位搜索的 savePage/saveDetail 会上传岗位对象，normalize_job 白名单保留 securityId，随后作为版本 payload 写入数据库。招聘聊天同步另有字段投影，不能将两条链路混为一谈。
- 验收目标：集中修订时明确岗位快照、聊天记录、模型上下文和登录凭据各自保存哪些字段；不能将岗位标识描述为登录 Cookie，也不能在介绍整个扩展时笼统承诺全部临时标识均不上传。本项仅记录文档范围问题，不据此新增安全框架或擅自删除现有字段。

### RUN-001 工具循环增长消息但未复测预算

- 入口：`src/career_assistant/response_runner.py` 的 `_complete_skill_agent`；`prompt_context.py` 的 `prepare`。
- 证据：初始 Prompt 完成预算后，Runner 会追加工具执行规则、assistant 工具请求及 tool 结果；六轮循环内没有再次调用预算服务。工具请求的输出 Token 上限不限制累积输入长度。
- 局部验证：实际工具循环使用模拟模型和模拟 Registry，工具结果追加后，两次模型调用的简化输入估算分别为 248 和 42248 Token，超长结果仍完整进入第二次调用。无真实模型或外部安装。
- 验收目标：后续模型调用前对实际消息集合复测预算；预算不足时明确处理工具结果和剩余执行条件，不仅依赖轮数限制或 Provider 报错。

### MAT-001 JD 要求遗漏未被发现

- 入口：`src/career_assistant/job_match_rules.py` 的 `validate_match`。
- 证据：验证模型给出的条件、维度和原文引用，但没有检查候选人要求是否被完整覆盖，也没有为未进入 items 的要求输出覆盖状态。Prompt 要求完整覆盖不等于后端已验证完整覆盖。
- 局部复现：JD 有活动策划和必须持有执业证书两条要求，模型输出只包含已满足的活动策划；实际验证器接受报告，核心为 100%，硬性为 `not_specified`。
- 验收目标：明确要求覆盖的检查和披露口径；遗漏明确门槛或覆盖不完整时，不能无提示地把报告展示为完整分析。不承诺通过简单行号覆盖就能解决全部语义漏项。

### MAT-002 条件类型可绕过确定性复算

- 入口：`src/career_assistant/job_match_rules.py` 的 `_condition`、`_deterministic`。
- 证据：只有 kind 不为 semantic 时进入数值、年限等规则；semantic 的 supported 主要验证有引用且不是 mention_only/none，没有检查 JD 中明确阈值与 kind 是否一致。
- 局部复现：JD 为“至少3年全职经验”，CV 为“仅有2个月实习经验”，模型将条件标记为 semantic/direct/supported；实际验证器仍返回满足及核心 100%。无真实模型调用。
- 验收目标：对明确可识别的数值、年限等条件建立类型一致性边界，不能通过选择 semantic 绕过复算；语义相关性仍需单独评测，不把引用存在等同于证据支持。

### MAT-003 负数被按正数计算

- 入口：`src/career_assistant/job_match_rules.py` 的 `_numbers` 与 number 条件分支。
- 证据：数字正则未包含正负号，`-10` 会提取为 `10`。
- 局部复现：JD 为“净利润至少5万元”，CV 为“个人负责项目净利润为-10万元”，引用均有效且 kind 为 number；实际规则把 actual 计算成 10 并返回 supported，预期应为 unsupported。
- 验收目标：保留数值符号并验证正负数、明确百分比及不支持格式的边界；无法可靠解析时返回待确认，不按错误数值判定。

### RAG-001 检索查询长度边界不一致

- 入口：`web/router.py` 的 `_build_interview_evidence`；`interview_library/repository.py` 的 `search_lexical_chunks`。
- 证据：公司、岗位和问题拼接后最多取 360 字符；关键词仓储以 240 字符验证。调用先做关键词检索，超长 ValueError 不会自动转成较短查询。
- 局部验证：调用实际仓储方法，241 字符查询在访问数据库前被拒绝。当前注入步骤位于 Turn 入队前，错误会影响受理。
- 验收目标：统一构造层和仓储查询长度规则，验证长问题、公司岗位前缀和显式面经引用的受理行为。

### RAG-002 自动检索误识别非面试请求

- 入口：`web/router.py` 的 `_is_interview_preparation_query` 与 `_build_interview_evidence`。
- 证据：只做子串匹配，“准备”等泛化词独立存在即可通过；没有结合请求内容确认面试意图。
- 局部复现：存在绑定目标岗位时，调用实际证据构造函数处理“准备一下晚饭菜单”，模拟检索服务观察到检索被触发。未调用真实知识库或模型。
- 验收目标：面试准备和明确面经选择正常召回，普通生活、业务准备等无关请求不因泛化词自动注入面经；不默认增加新的模型调用。

### REC-001 过期租约缺少持续回收

- 入口：`src/career_assistant/turn_worker.py` 的 `run_forever`、`_fill_capacity`；`persistence/turn_job_repository.py` 的 `recover_expired`、`claim_next`。
- 触发：Worker 退出后在旧租约到期前重新启动；启动回收未命中，后续租约到期。
- 证据：生产运行路径只在进入轮询前调用一次 `recover_expired`；后续领取只查找 queued 任务。
- 验收目标：启动后才过期的任务也能被发现并按现有恢复规则处理，恢复后同会话可以继续使用。

### REC-002 SSE 重连重复追加正文

- 入口：`web-ui/src/components/CareerAssistantPage.vue` 的 `requestSse`、`observeNextServerTurn`；`web-ui/src/career-turn-client-queue.js` 的 `upsertServerTurn`。
- 证据：后端支持 `id` 和 `Last-Event-ID`；前端解析器未读取 `id`，重连请求未发送游标，同时保留已有 `streamedText`。
- 局部复现：提取实际 `requestSse` 函数并模拟断线，第一次收到“第一段”，第二次重放“第一段”和“第二段”，最终拼接为“第一段第一段第二段”。无真实网络请求。
- 验收目标：同页断线重连和刷新后重建显示均无重复、无缺段；最终消息只出现一次。
- 边界：最终 done 消息或重新读取会话可以校准最终正文，本项主要影响重连期间的流式显示。

### REC-003 任务重跑重复持久化用户消息

- 入口：`src/career_assistant/intake_graph.py` 的 `_persist_history`；`persistence/conversation_repository.py` 的 `append_message`。
- 触发：用户消息已保存，但 Turn 尚未进入终态时 Worker 退出；租约回收后整轮重跑。
- 证据：输入处理图每次执行都会追加用户消息，仓储使用新 UUID 插入，未按 Turn 复用已有用户消息。
- 局部复现：对相同 Turn 调用实际 `_persist_history` 两次，模拟仓储观察到两次用户消息插入调用；尚未做真实 PostgreSQL 崩溃恢复集成验证。
- 验收目标：同一 Turn 恢复执行后仅保留一条对应用户消息，新一轮正常输入仍可独立保存。

## 已确认的能力边界

- 当前恢复分为页面事件重放和整轮任务重新执行；LangGraph 未配置 checkpointer，不提供节点级或模型生成 Token 级续跑。是否扩展需在讨论中明确，不能直接增加一套恢复框架。
- 普通用户会话最多 30 轮成功回复，达到上限后要求新建会话。这是现有产品限制，是否调整尚未决定。
- 求职长期记忆当前停用。旧会话续聊使用原 conversation_id 下的历史、摘要和绑定档案；新会话不会自动继承旧会话聊天偏好。
- 原始附件文件清理后，当前任务仍可从数据库 payload 恢复已解析文本和请求上下文；不能据此声称所有附件解析正文均未持久化。
- 摘要和历史正常同时注入，历史按摘要覆盖位置去重；页面展示的原始记录与模型本轮收到的消息集合不同。没有有效摘要时使用未摘要的历史，最终仍受上下文预算约束。
- 打开旧会话不会主动生成新的聊天回答或重新生成会话摘要；有未结束任务时恢复观察。已绑定简历和岗位的会话还可能补跑或刷新岗位匹配评估，因此不能把页面打开描述为绝不触发任何模型调用。
- 正常落库的用户消息和最终助手回复逐条保留，摘要不会删除这些原文；历史文本受处理策略和长度限制影响。附件原文件、输入 payload、流式事件及消息历史属于不同记录，不能概括为所有原始交互均无损写入聊天历史。
- 文档解析与主对话模型分开：图片先 Docling OCR，最低文本门槛未满足时调用平台视觉模型，后续聊天只接收文本。当前扫描 PDF 增强解析失败没有自动逐页视觉复核路径。
- 当前基准简历解析和附件 Turn 提交都在 API 阶段调用解析器，后者完成解析才保存 Turn 并交给 Worker。对话 Worker 的并发和租约机制尚不覆盖入队前 OCR；是否调整属于后续架构讨论，不默认扩大修复范围。
- 当前消费 Docling Markdown，未实现带页码、区块坐标和置信度的统一 Document Graph，也未接入独立 PaddleOCR PP-StructureV3 备用解析器。旧设计文档需在集中处理时区分现有实现与规划。
- 新版动态指标采用 JD 生成维度、硬性/核心/加分三层、条件树及服务端区间计分；判断原文相关性和语义支持仍依赖 Judge。LLM 失败时可能生成明确标识的旧版词法降级报告，不能与新版算法混为一谈。
- 浏览器面试大师使用授权系统音频、AudioWorklet、24kHz PCM16/100ms 分帧、WebSocket、流式 ASR 和文本模型；面试官 final 触发连接内 asyncio FIFO。普通问题只用当前问题，追问最多携带当前问题之前的 4 条转写，不自动注入简历、JD、面经或长期摘要。
- 实时面试的回答队列位于连接内存中；断开连接时取消当前任务并清空队列。数据库保存最终转写和回答供历史查看，当前不支持跨连接恢复原 ASR 现场或未完成队列，不能套用普通对话的租约恢复描述。
- 主对话 Runtime 由数据库调度、七节点顺序输入图和 Runner 组成；`CareerAgentLoop` 主要管理生命周期，模型工具循环位于 Runner。输入图没有回边，只有满足条件的显式 Skill 才进入最多六轮工具决策，普通聊天直接流式生成。
- Skill 支持同会话继承：本轮没有有效 `/name` 时，回溯最近用户消息中的显式调用，重新读取正文并展开当前任务参数。当前调用覆盖继承；自动简历初评的单次 Skill 不因此继承。前述“显式 Skill”包括源于之前显式调用的 session 来源，不应描述为每轮都必须重新写 Slash。
- 面经按当前请求的选择或意图重新检索；不自动把上轮检索片段原样永久挂载。知识数据封装与已激活 Skill 指令分开，实际 Tool 能力仍由 Registry 提供。
- BOSS 岗位列表、详情与招聘聊天由本机扩展注入已登录 BOSS 标签页，调用其网页内部接口；服务端保存归一化数据。当前岗位搜索页会串行预取完整 JD，同一搜索生命周期复用详情缓存；对话模式按搜索批次和版本持久化，模型按预算读取快照，不在工具循环中直接控制 BOSS。
- Chrome 扩展 Service Worker 的请求串行队列在内存中，与 PostgreSQL Turn Worker 的租约、任务恢复不同。招聘沟通页面每 30 秒尝试同步，仍要求页面可见、扩展与登录有效且拥有活动执行资格；不能理解为服务器持续代收 BOSS 消息。
