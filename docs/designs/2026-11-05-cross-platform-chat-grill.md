# 跨平台消息方案压力审查

日期：2026-11-05（北京时间），状态更新于 2026-11-09。公开资料核对、现有实现审查和离线故障注入已完成；九项产品决策均已确认，已整理为 [BOSS 双向沟通设计](2026-11-05-boss-chat-bridge-design.md)。BOSS 本地入站接收已实施，见 [收件模块](../modules/boss-inbox.md)；真实账号及完整双向沟通仍待验证，下文的原发送压力结果不是新收件模块的实测结果。

## 审查结论

1. **存在检测、拦截和拒收的可能，不能承诺零检测或全部送达。** 本地登录态、串行执行、每批 1–10 岗位都不是免检测保证，也不是平台公开认可的安全阈值。
2. **BOSS 求职者双向沟通有技术实现途径。** 可组合求职者会话/历史读取与本地官方聊天页发送；目前没有在本项目账号完成完整双向闭环。
3. **现有一键打招呼不能直接充当持续聊天系统。** 缺少接收动作与会话身份核验，首次建联和后续回复语义不同，点击后的拒收不可见，网页超时也不取消已排队的后台动作。
4. **不能直接把 BOSS 聊天页嵌入我们网站。** 本次官方聊天页 CSP 的 frame-ancestors 不包含我们的域名。
5. **猎聘和前程无忧不能因 BOSS 可行而视为同时可行。** 猎聘有 PC 自定义聊天源码线索；前程无忧当前公开 PC 沟通组件引导微信/App，仍缺可直接采用的求职者网页消息通道证据。

## 本地故障注入结果

执行现有真实 runChatSend、网页 bridge 与 Service Worker 串行分发器，替换 DOM、计时器和业务处理器为内存模拟。10 类场景各执行 100 次，共 1,000 次。没有访问浏览器、招聘平台、真实模型或用户私聊。

这些是确定性反例的重复验证，不是 1,000 条真人消息的送达压测；断言成立代表观察到了预期的现有行为，不代表业务可靠性通过，也不能用于计算真实拒收率。

## 检测与拒收的不同层级

| 层级 | 可核实事实或风险 | 设计应如何表达 |
| --- | --- | --- |
| 浏览器事件 | 脚本 click/dispatchEvent 与用户事件存在标准定义的 isTrusted 差异 | 不能宣传插件行为不可被识别；不能仅凭此断言 BOSS 当前按该字段拦截 |
| 平台风控 | BOSS 隐私政策明确会利用行为、设备/IP 和服务日志排查异常 | 没有可承诺的固定安全次数/间隔；验证与限流要以当前状态为准 |
| 登录与身份 | 本地会话失效、切号、额外核验会改变可用能力 | 扩展在线不等于账号和聊天已就绪；切号后不能沿用旧会话身份 |
| 建联与额度 | 首次开聊与已存在会话回复是不同动作；平台额度和规则可能不同 | 分离首次招呼与继续回复，不能每次都 friend/add，也不猜固定额度 |
| 内容 | 当前官方聊天代码含附件简历被限制发送的明确界面分支 | 文本、外链、附件分开验证；没有证据认定所有 URL 必被拒收 |
| 接收者 | 本次没有获得当前求职端被拉黑/拒绝陌生消息的完整官方规则 | 明确失败按原文展示；HR 不回复不等于技术拒收 |
| 异步提交 | 点击、页面气泡、传输 ACK、业务接受和对方已读不是同一状态 | 只展示可证实层级；无业务证据时保留未知，不自动重发 |
| 浏览器生命周期 | 后台标签页可能冻结/丢弃；MV3 后台存在终止条件 | 本地同步依赖实际在线状态，不能承诺浏览器关闭后持续收取 |

来源：[DOM 标准](https://dom.spec.whatwg.org/#dom-event-istrusted)、[BOSS 当前隐私政策](https://about.zhipin.com/agreement?id=personalinfopro)、[BOSS 当前用户协议](https://about.zhipin.com/agreement?id=registerprotocol)、[官方聊天 bundle](https://static.zhipin.com/fe-zhipin-geek/web/chat-new/v5575/static/js/app.01b38f51.js)、[Chrome 页面生命周期](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)、[MV3 后台生命周期](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)。

官方聊天页还加载 browser-check、security 和遥测类脚本。脚本名称不能证明具体自动化检测规则，更不能据此给出规避规则的承诺。

平台授权与技术可行性也须分开。BOSS 当前官网链接的用户协议四.11、七.5涉及未经许可的第三方工具接入，八.1涉及功能限制等处理；前程无忧现行条款也有第三方插件获取数据的限制。这里只报告适用的产品依赖，不将用户账号登录等同于平台接入许可。[BOSS 协议](https://about.zhipin.com/agreement?id=registerprotocol)、[51job 条款](https://we.51job.com/service)

## BOSS 跨平台沟通的候选途径

### 优先验证 本地浏览器消息桥

用户在我们的独立沟通页面选择 BOSS 会话，扩展在本人已登录浏览器读取联系人和消息；用户在我们平台确认一条回复，扩展定位同一会话并单次提交到官方页面，随后读取可证实的结果。

~~~mermaid
flowchart LR
  UI[我们平台的沟通页面] --> BRIDGE[现有插件桥]
  BRIDGE --> READ[求职者会话与消息读取]
  BRIDGE --> SEND[官方聊天页单次发送]
  READ --> BOSS[BOSS 当前账号会话]
  SEND --> BOSS
  BOSS --> RESULT[消息与提交结果]
  RESULT --> UI
~~~

可新增 list_conversations、get_messages、reply_message。reply_message 是持续对话能力，不复用 send_greeting 的首次建联或 retry_greeting_message 的失败恢复语义。

用户现已确认：列表与摘要先同步，正文按需读取；平台保存最近 30 天已取得的记录；用户逐条确认发送，不自动回复。当前资料只证明存在技术路线，没有完成本项目的账号验收。

- 已读的历史读取封装中未发现额外 mark-read 调用，但这不能证明服务端 GET 无副作用；导航、自动选中和点击 DOM 会话是否产生已读回执，也尚未证实。不能承诺同步绝不影响 BOSS 未读，更不能为同步正文自动逐个打开全部会话。[历史读取实现](https://github.com/jackwener/OpenCLI/blob/97dc0cd5214b9602bcda78d7422f231ee8a803e9/clis/boss/utils.js#L461-L478)

## 从首招升级为持续聊天必须解决的功能点

- **会话身份**：平台、当前账号 UID、对方 UID/会话 ID 共同定位。岗位只是关联上下文；同一 HR 可能对应多个岗位，不能继续仅按 platform:jobId 管理会话。
- **动态字段**：securityId 等运行时令牌不能当永久联系人键，发送前使用当前会话信息核对。
- **消息身份**：按平台消息 ID、方向和原始时间去重；文本相同可以是两条合法回复。“好的”不能因以前说过就禁止再发。
- **输入与提交**：检测人工草稿；填写前及提交前重新核对账号、对象、限制状态，防止切会话时误发或覆盖。
- **后台未开始任务**：网页取消、过期或失联后，后台在真正执行前还需核对是否应继续；已经点击的动作不能承诺撤回。
- **结果层级**：submitted 只表示提交动作；业务接受、明确失败、未知、已读分开。不能因输入框清空或 MQTT ACK 直接展示对方已收到。
- **增量与断线**：页面渲染的气泡只是一部分历史；虚拟列表、换会话、重绘、令牌变化和休眠恢复都要验证，不能宣称一次 DOM 抓取取得完整历史。
- **界面任务**：按项目规则，完整聊天应有独立沟通子路由，保持选岗/首招弹窗聚焦首次联系。

## 分层验证建议

1. **已完成的本地反例验证**：上述 1,000 次离线注入已经证明现有处理边界，优先据此定义聊天接口及验收状态。
2. **下一步只读账号验证**：本人登录后读取两个已存在的求职者会话，核对同名 HR、多岗位、消息 ID、发送方向、时间、分页与当前账号。打开会话可能影响平台未读状态，须作为真实页面行为说明。
3. **受控单条收发验证**：用户看见目标现有会话与最终文本后确认一条；核对 BOSS 侧结果，并在有真实回复时验证回读同一会话。没有真实业务回执/回复，不宣称双向闭环已经通过。
4. **本地并发与故障回归**：对自有桥接/模拟页面测连续点击、多个视图、前置队列阻塞、重载、切号、断网和异步拒收。真实平台只做正常低量验收，不用高频试探风控阈值估算所谓安全次数。

## grilling 决策树

第一轮用户已确认：

1. 沟通范围：读取 HR 回复，并在我们平台继续对话。
2. 运行条件：接受用户本地浏览器在线时同步；用户保持 Chrome/Edge 与 BOSS 登录，打开我们的沟通页面时同步。
3. 发送决策：用户确认每条消息后发送，AI 可辅助起草，不自动发送。

第二轮 Q4 用户已确认：聊天记录保存到我们平台，支持历史查询和换设备查看。换设备查看已保存记录与实时同步分开：新消息的取得和发送仍遵循第一轮已确认的本地浏览器在线条件。

第二轮 Q5 用户已确认：同步会话列表与最新消息/未读摘要；用户点开某会话后再按需读取正文，不自动同步全部会话正文。

第二轮 Q6 用户已确认：验证码、登录失效或限流属于平台账号级问题，暂停该账号后续动作；人工处理后手动继续。岗位失效等单项问题仍可跳过，不据此暂停整个账号。

第三轮 Q7 用户已确认：首期只做文本收发；图片、附件和语音显示真实类型及到 BOSS 查看入口，不展示为空消息，也不宣称已支持这些类型收发。

第三轮 Q8 用户已确认：已同步到平台的聊天记录仅保留最近 30 天，不采用长期保留方案。

第三轮 Q9 用户已确认：接受打开会话后平台正常的已读行为；不为同步摘要而自动逐个打开未选会话，不承诺隐形阅读。

仅保留本地浏览器在线的执行通道，不把关机后的全天候运行或 AI 自动发送纳入本轮设计。2026-11-09 已完成本地入站读取、历史持久化与 PC 页的模拟验证；真实账号收件和持续发送仍待验。

### 2026-11-09 复审第一轮

用户以“听你的”确认以下三项建议，作为原九项范围的补充：

1. **源正文补齐**：已打开会话必须支持按需补齐源平台仍可取得的最近 30 天历史；恢复时追至已确认同步边界，无法补齐则显示缺口。未选会话继续只同步摘要。
2. **前台同步**：首期接受仅沟通页面可见时同步；切回前台后立即尝试补齐，暂停账号仍须人工处理并手动继续。不承诺后台常驻收件。
3. **单活动执行端**：同一平台用户的同一 BOSS 账号只保留一个活动执行端，其他页面或设备查看平台历史；账号暂停由执行层统一约束。

本轮代码审查与内存模拟确认了两个实现缺口：网页桥和 Service Worker 未传递源分页参数，正文 has_more 未继续消费；账号限流仅暂停当前页面，其他页面及扩展下一条请求仍可继续。数据库翻页及单页面暂停测试不覆盖这两个问题。绑定第二账号的疑点已排除：PC 账号选择器提供“同步当前浏览器账号”入口。

本轮结束时的决策树：原九项范围 → 历史补齐、同步条件、活动端规则已确认 → 接管规则、待发操作有效性、未知结果核对进入第二轮。后续决定见下节。

### 2026-11-09 复审第二轮与结论

用户再次以“听你的”确认本轮三项推荐：

1. **手动接管**：新页面默认查询历史，点击“在此接管”后等待旧端资格失效，再开始源平台操作。新端不继承旧端的待发重放责任；待核对消息不重新发送。
2. **离页与超时失效**：尚未触发提交的操作失效，回来后重新确认。已触发提交或无法确认是否触发的，只核对结果，不能展示为已取消。取消须先更新操作有效状态，不能排在待发任务之后。
3. **未知结果收场**：保留“待核对”并提供到 BOSS 查看入口，旧操作不重发。新消息另行确认；不能靠相同正文、接近时间或乐观界面猜测旧消息成功。

发送技术契约按以上决定细化：独立 external_chat_operations 保存操作 ID、冻结目标与正文、状态及有效期；同 ID 重复请求仅查询现有状态。初始执行有效期为确认后 30 秒，重载、失联和接管不恢复旧操作。操作正文依照既定 30 天规则清理，执行期限与内容保留期限分别计算。现有消息三表没有这些操作字段，不用伪造平台消息 ID 或时间适配待发记录。

### 平台保存聊天的已核实基础

用户选择服务器保存后，可复用现有 CareerDatabase 的 PostgreSQL/SQLAlchemy 连接与事务、API 登录身份和按 actor_id 过滤的仓储模式。src/web/api.py 将平台登录用户 ID 映射为 actor_id，同一平台用户换设备不改变这一归属。

外部账号、会话和消息应使用独立的 external_chat_* 数据与仓储。现有 career_assistant.messages 的角色仅供 AI 对话使用，response_runner.py:839 会将其中 user/assistant 历史自动拼入模型请求；直接存入 HR 聊天会混淆来源和默认扩大模型输入范围。外部聊天的保存不等同于授权将全部聊天自动送给模型。

采用外部平台账号、外部会话、外部消息三类记录，保留所属用户、平台账号 UID、对方 UID、平台消息 ID、方向、类型、正文、原始时间和提交状态。正文按需同步，仅保留最近 30 天；非文本只保留必要的类型和占位信息，不保存媒体文件。

跨设备查看应展示最后同步时间，并区分已有历史与当前浏览器能否实际发送。换设备读取已保存记录不代表该设备已安装插件或登录对应 BOSS 账号。
