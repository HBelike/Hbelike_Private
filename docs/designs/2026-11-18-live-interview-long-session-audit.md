# 45～90 分钟连续面试架构核查

## 判断

45～90 分钟处于当前设计时长范围内：前端单场墙钟上限为 120 分钟，ASR 官方音频输入时长不限，后端没有 45/60/90 分钟总时长限制。固定长度上下文不会随面试时间持续增长。

但目前只能说“设计支持”，不能说“整场可靠性已完成验证”：本轮真实生产链路验收为 75 秒，尚未执行真实 45～90 分钟持续音频 soak；断连恢复和跨多轮语义一致性仍有明确边界。

## 公开模型限制

- [百炼实时 ASR 用户指南](https://help.aliyun.com/zh/model-studio/real-time-speech-recognition-user-guide)：`qwen-audio-3.1-asr-flash-streaming` 使用限制表中大小/时长为“不限”。因此 45～90 分钟没有超出公开音频输入限制；这不是网络不中断的承诺。
- [Streaming 客户端事件](https://help.aliyun.com/zh/model-studio/qwen-audio-asr-streaming-client-events)：`heartbeat=true` 配合持续发送静音音频可保持静音期间连接；仅发送 WebSocket Ping 不能代替有效 PCM 输入。当前 Provider 已设置该参数，AudioWorklet 正常时会持续发送静音 PCM。
- 当前代码使用标准 `DASHSCOPE_API_KEY`，没有在浏览器暴露临时 Key；没有 30 分钟临时凭据到期路径。

## 本地与线上链路边界

| 项目 | 当前实现 | 45～90 分钟影响 |
| --- | --- | --- |
| 前端计时 | 115 分钟提示，120 分钟结束；暂停采集仍计时 | 45～90 分钟不触发截止 |
| WSS 鉴权 | 建立连接时校验；默认会话 idle 7 天、absolute 30 天 | 没有 45 分钟到期逻辑 |
| 反向代理 | 生产 Caddy `/api/*` 直达 API，无总时长配置 | Nginx 的 15 分钟空闲超时不在生产 API 路径中 |
| ASR | 同一 WSS 内持有一个 task，持续音频+heartbeat | 没有主动按 45 分钟断开；也没有 task 自动重建 |
| 转写历史内存 | 最近 12 条 | Token/内存规模有界 |
| 模型 prompt | 普通问题仅当前题，追问取此前 4 条转写 | 不会把整场音频转写累计进上下文 |
| 页面记录 | 转写最多 100 条，本场问答最多 50 条 | 超出仅截断页面缓存，数据库保留全量 |
| 音频缓存 | 每轨最多 20 帧，单次发送超时 3 秒 | 避免持续积压导致几十秒心跳阻塞 |
| final sequence 集合 | 随 final 句数增长 | 45～90 分钟几百～几千个整数通常很小 |
| 回答 FIFO | 每场串行、无队列长度上限 | 长期提问速度超过完整生成速度时会累计等待 |

关键源码：`BrowserInterviewMasterPage.vue` 的 `startTimer/handleConnectionState`，`live_interview/session_manager.py` 的 `_handle_transcript/_read_asr`，`answer_service.py` 的 `build_answer_prompt`，`question_detector.py` 的 `detect`，`asr/dashscope_realtime.py` 的 `events`。

## “连续对话记忆”的实际含义

当前四条历史是“最近四条 ASR final 转写”，可能混合面试官和候选人的语音转写，**不包含模型先前生成的答案**。仅识别为 `FOLLOW_UP` 的问题使用这四条历史；判定仍依赖“继续、刚才、那如果、进一步”等标记词。

因此同知识点短追问通常能获得最近转写指代，但下列场景未被完整覆盖：

- 面试官引用模型上一份答案中的某一结论，而该答案没有被候选人真实说出来。
- “它为什么这样”“这个呢”等没有现有追问标记的省略式问句。
- 追问关联内容已经超过四条转写窗口。

这是语义连续性限制，与模型可容纳 1M Token 或面试总时长无直接关系。本轮按用户要求只调研，不更改原有记忆设计。

## 断连和 ASR 自然结束

活动期 WSS 断连会暂停采集并释放音轨，需要重新选择声音来源；自动重试仅覆盖首次建立未 ready 的一次重试。重连会创建新的 session 和 manager，不从数据库恢复四条上下文。

ASR 收到 `task-finished` 会自然结束 reader，manager 对正常意外 EOF 尚无专门终态提示或任务重建。没有发现 45 分钟必然触发该事件的证据，但长场次应覆盖这个异常场景。

归档接口最多接受 20 个 session；只有同一场频繁重新连接时才可能接近该边界。

## 验证状态与下一步

- 已完成：真实本地 TCP 的慢上游复现/修复、75 秒持续连接、8/32 并发、生产真实 ASR+模型+公开 WSS 75 秒验收。
- 未完成：真实 45～90 分钟持续语音、长静音、网络短断与重新接续的全场验收；不能用 75 秒结果替代。
- 最有价值的下一项验收：90 分钟单连接，混合至少 30 个知识问题与连续 3～4 轮追问，穿插 3～5 分钟静音；检查无静默停止、无持续队列增长、会话记录完整、内存稳定，并核对追问指代。
- 若要提升产品保证：优先补齐 ASR 意外结束提示与连接恢复，再按用户决定是否扩展为有界最近问答记忆；无需先扩充全场 prompt。
